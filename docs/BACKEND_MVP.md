# ТЗ бэкенду: MVP совместного холста «Рядом»

Версия: 12 сентября 2026. **Это задание на реализацию, а не описание готового API.** Документ заменяет прежние требования в BACKEND_BOARD.md и BACKEND_HANDOFF.md. Использовать существующий C++ / Drogon и PostgreSQL. Существующие заметки и пользователей не удалять.

## 1. Что должно получиться

Пользователь входит в аккаунт, создаёт приватную доску и работает один. При желании отправляет ссылку другому человеку. После входа по ссылке они одновременно рисуют, пишут, перемещают объекты и добавляют файлы. Через месяц или с другого устройства пользователь открывает ту же доску со всеми сохранёнными данными.

**Источник истины — серверная БД и серверные файлы.** IndexedDB допускается только как кэш и очередь неподтверждённых изменений. Ответ «сохранено» отправлять после записи на сервер. Очистка браузера не удаляет подтверждённые данные. Ручной экспорт/импорт не заменяет серверное сохранение.

### Принятые ограничения MVP

- Один экземпляр API, одна PostgreSQL, файлы в постоянном Docker volume. Без Redis, S3, микросервисов и CRDT.
- До 10 одновременно подключённых сессий на доску. Две вкладки одного пользователя — две сессии. Пользователь может иметь несколько досок.
- Все участники входят в аккаунт; анонимное редактирование не нужно.
- Две роли: owner и editor. Оба редактируют и скачивают файлы; только owner переименовывает доску, создаёт/отзывает приглашение и удаляет участников. Viewer и передача владения не нужны.
- Разные объекты редактируются параллельно. Одновременные правки одного объекта проверяются по revision: первая сохраняется, вторая получает явный конфликт. Посимвольное объединение одного текста не требуется; молчаливая потеря второго варианта запрещена.
- PDF/Office — вложения для скачивания, без встроенного редактора. История версий, комментарии, удаление досок/аккаунтов, публичный каталог и полноценная офлайн-работа не входят в MVP.

## 2. Что использовать из текущего проекта

В `todo_list_cpp/controllers/UserController.h` есть register/login/refresh/me и logout на всех устройствах. Вход принимает `{email,password}`, возвращает `data.access_token` и `data.refresh_token`. Переиспользовать пользователей и JWT, проверить эти маршруты интеграционными тестами. Старые API заметок оставить совместимыми.

Для досок добавить отдельные таблицы и `/api/v1/boards`. Не записывать весь холст в `notes.content` при каждом изменении: это затирает параллельные правки.

Сейчас фронтенд работает локально через IndexedDB/BroadcastChannel. API заметок используется только для отдельных снимков без оригиналов файлов. **Новый backend потребуется подключить к фронтенду отдельной задачей — раздел 11.** Наличие запущенного API само по себе не включает совместность.

## 3. База данных и миграции

Предоставить версионированные SQL-миграции: создание существующей схемы users/refresh_tokens/notes/users_notes на пустой БД и добавление таблиц доски. Существующую БД обновлять без удаления данных. Модели Drogon не заменяют миграции.

Новые ID доски/объекта/файла/операции — UUID. Тип user_id совпадает с существующим users.id. Во внешнем JSON все ID — строки. revision/serverSeq — целые числа от 0 до `9007199254740991`.

| Таблица | Обязательные поля и ограничения |
| --- | --- |
| boards | id UUID PK, owner_id FK users, title VARCHAR(180), server_seq BIGINT DEFAULT 0, created_at, updated_at |
| board_members | board_id FK boards, user_id FK users, joined_at; PK (board_id,user_id). Здесь только editors; owner определяется по boards.owner_id |
| board_objects | board_id FK boards, object_id UUID, type, payload JSONB, attachment_id nullable, revision BIGINT, deleted BOOLEAN, created_at, updated_at; PK (board_id,object_id) |
| board_operation_receipts | board_id FK boards, op_id UUID, actor_id FK users, request_hash, result JSONB, server_seq BIGINT, created_at; PK (board_id,op_id), UNIQUE (board_id,server_seq) |
| board_attachments | id UUID PK, board_id FK boards, uploaded_by FK users, upload_id UUID, storage_key UNIQUE, original_name, mime, size BIGINT, sha256, created_at; UNIQUE (board_id,uploaded_by,upload_id) |
| board_invites | board_id PK/FK boards, token_hash UNIQUE, expires_at, created_at; максимум одна действующая ссылка на доску |

В payload хранить редактируемые поля; id/type/revision/deleted/created и attachmentId собирать из колонок, не хранить расходящиеся копии. Добавить составной FK `(board_id,attachment_id)` на вложение той же доски и соответствующий UNIQUE `(board_id,id)` у вложений. Индексы: список досок по владельцу и участнику, объекты/вложения по board_id. Даты — TIMESTAMPTZ, HTTP — UTC ISO 8601; только object.created отдавать миллисекундами Unix для совместимости с фронтендом.

Изменение объекта, увеличение revision и boards.server_seq, обновление updated_at, запись результата операции — **одна транзакция**. ACK отправлять после COMMIT. Для MVP допустим короткий SELECT FOR UPDATE строки boards на время транзакции; не держать блокировку, пока пользователь печатает. Проверка прав/отзыв доступа используют тот же порядок блокировок, чтобы операции и отзыв имели однозначный порядок.

Удалённые объекты остаются с deleted=true. Их строки и результаты успешных операций не очищать по времени в MVP. UUID удалённого объекта нельзя повторно создать. Это обеспечивает безопасные повторы запросов и восстановление объектов.

Миграции регистрировать в schema_migrations, применять один раз под блокировкой. При ошибке миграции API не стартует. Проверить миграции и на пустой БД, и на копии старой схемы.

## 4. HTTP API досок

Новые HTTP-маршруты досок/файлов требуют `Authorization: Bearer <access_token>`. Исключения: health без авторизации и WS handshake с одноразовым ticket (раздел 6). Register/login/refresh сохраняют существующий способ авторизации. Автор определяется из проверенного токена, не из userId запроса. Успех: `{"status":"Success","data":...}`. Ошибка: `{"status":"Error","code":"...","message":"..."}` с настоящим HTTP-кодом ошибки. Если ниже не указан иной код успеха, использовать HTTP 200; создание доски — 201. objects/attachments/items всегда массивы, включая пустые; метаданные attachment в снимке имеют тот же формат, что ответ upload.

| Метод и путь | Вход → результат в data |
| --- | --- |
| POST /api/v1/boards | `{title}` → `{id,title,role:"owner",serverSeq:0}`; создать пустую приватную доску |
| GET /api/v1/boards?limit=50&offset=0 | `{items:[{id,title,role,updatedAt}],nextOffset:null}`; свои и приглашённые, updatedAt DESC и id как второй ключ; limit 1–100 |
| GET /api/v1/boards/{id} | `{id,title,role,serverSeq,objects,attachments}`; согласованный снимок неудалённых объектов и метаданных используемых ими вложений |
| PATCH /api/v1/boards/{id} | `{title}` → `{id,title}`; только owner, 1–180 символов после trim |
| POST /api/v1/boards/{id}/operations | Одна операция из раздела 5 → подтверждение или конфликт |
| GET /api/v1/boards/{id}/members | `{items:[{userId,displayName,role}]}`; включая owner, без email |
| DELETE /api/v1/boards/{id}/members/{userId} | Только owner удаляет editor → `{removed:true}`; повтор безопасен, owner удалить нельзя |

Неверный/истёкший токен → 401. Недоступная или отсутствующая доска/файл → 404, включая попытку угадать ID. Запрещённое действие уже известного участника → 403. Неверная схема → 422; слишком большой запрос → 413; квота → 409 BOARD_LIMIT; частота → 429 с Retry-After; недоступная БД/хранилище → 503, без успешного ACK.

Снимок читать в согласованной транзакции, например REPEATABLE READ: objects должны соответствовать serverSeq. Файловые байты в JSON не включать. Переименование отдельно рассылать как `{"type":"board.updated","title":"Новое имя"}`; оно не увеличивает object revision/serverSeq. serverSeq относится только к операциям объектов.

## 5. Операции и конфликты

### Объекты

```json
{
  "id":"f53c8fca-83bc-4db0-a8d3-757a536852cb",
  "type":"sticky", "x":120, "y":180, "w":240, "h":180,
  "text":"Наша идея", "color":"mint",
  "revision":1, "deleted":false, "created":1789200000000
}
```

Типы: sticky/text/shape/stroke/image/file. Shape — прямоугольник. Общие редактируемые поля: x/y/w/h/text/color. Для text допустимы headline/small boolean. Для stroke обязательны points `[[x,y],...]` относительно начала объекта. Для image/file обязателен attachmentId; mime/size возвращать из серверного вложения. text у файла — подпись; originalName — имя оригинала.

ID/type/attachmentId после создания не меняются. created/revision/deleted задаёт сервер. Не принимать локальные blobId, blob: URL, asset и произвольные внешние URL. Неизвестные и неподходящие типу поля отклонять, не игнорировать.

Ограничения: 1000 неудалённых объектов; text ≤20 000 UTF-16 code units (как JS .length); color только mint/blue/neutral; конечные x/y в ±1 000 000; 0 < w/h ≤1 000 000. Stroke: 1–10 000 точек с конечными координатами в ±1 000 000. JSON операции ≤1 MiB. Проверять всё на сервере, не полагаться на UI.

### Один способ записи: HTTP. WebSocket доставляет результат

Все постоянные create/update/delete/restore выполняются POST operations. Пример:

```json
{
  "opId":"5cfca326-3743-4652-aea8-75d99c7529fd",
  "objectId":"f53c8fca-83bc-4db0-a8d3-757a536852cb",
  "action":"update", "baseRevision":1,
  "patch":{"x":160,"y":200}
}
```

- create: baseRevision=0, вместо patch поле object с id=objectId, type и остальными полями без revision/deleted/created. UUID не существует, включая удалённые объекты. Созданная revision=1.
- update: patch только редактируемых полей; объект не удалён, baseRevision совпадает с текущей.
- delete: без patch/object, установить deleted=true при совпадении baseRevision.
- restore: без patch/object, восстановить удалённый объект с прежними полями при совпадении baseRevision; проверить квоту.
- Успешные update/delete/restore увеличивают revision на 1; любое успешное действие увеличивает serverSeq на 1. Delete возвращает полный объект с deleted=true.

Успех HTTP 200 для всех действий:

```json
{"status":"Success","data":{
  "opId":"5cfca326-3743-4652-aea8-75d99c7529fd", "serverSeq":42,
  "object":{"id":"f53c8fca-83bc-4db0-a8d3-757a536852cb","type":"sticky","x":160,"y":200,"w":240,"h":180,"text":"Наша идея","color":"mint","revision":2,"deleted":false,"created":1789200000000}
}}
```

Повтор того же opId тем же автором с тем же смысловым JSON возвращает прежний ACK, даже если объект позже изменился. Без новой revision/seq и повторной рассылки. Другой payload/автор под тем же opId → 409 OP_ID_REUSED. Проверять сначала текущий доступ, затем receipt, затем baseRevision. Неуспешные действия seq не увеличивают, успешный receipt не создают. Исправленная операция получает новый opId.

Для request_hash использовать SHA-256 нормализованного после валидации запроса: фиксированный порядок полей, одинаковое представление чисел, сохранение порядка массивов. Пробелы и порядок ключей входного JSON не должны менять результат. Одновременные повторы одного opId также выполняют действие только один раз.

При устаревшей baseRevision HTTP 409:

```json
{"status":"Error","code":"REVISION_CONFLICT","message":"Объект уже изменён","data":{"opId":"5cfca326-3743-4652-aea8-75d99c7529fd","currentObject":{"id":"f53c8fca-83bc-4db0-a8d3-757a536852cb","revision":3},"serverSeq":43}}
```

currentObject в примере сокращён; **в реальном ответе обязателен полный объект**, включая deleted. Неизвестный objectId → 404 OBJECT_NOT_FOUND; create с занятым UUID → 409 OBJECT_EXISTS с полным currentObject. Операция над неподходящим состоянием (например, update удалённого объекта) → 409 OBJECT_STATE_CONFLICT с полным currentObject.

Пример текста: А и Б начали с revision=2. А сохранил «Первый вариант», получил revision=3. Б отправил «Второй вариант» с baseRevision=2 → 409 с первым вариантом. Сервер текст А не заменяет. Клиент сохраняет черновик Б и предлагает создать отдельный стикер с новым UUID/opId. Если доска заполнена, черновик остаётся доступен для копирования. Undo — обратная операция с проверкой revision, не откат чужих изменений.

Клиент отправляет координаты во время перемещения до 5 раз/с и обязательно в конце; текст через 300 мс паузы и при выходе из блока. Штрих сохраняется после окончания рисования, до этого только preview. Неотправленный текст/незаконченный штрих не называть сохранённым. Лимит сервера — 20 операций/с на пользователя на доску, burst 40; при 429 очередь клиента остаётся.

## 6. WebSocket и восстановление соединения

1. POST `/api/v1/boards/{id}/session` с Bearer → `{ticket,expiresAt}`. Случайный одноразовый ticket, срок 30 секунд, привязан к пользователю/доске. Можно хранить в памяти единственного API.
2. Подключение `/api/v1/boards/{id}/events?ticket=...`. Проверить ticket, доступ и Origin из разрешённого списка. Access/refresh в URL не передавать; ticket исключить из логов.
3. Сервер сначала подписывает сессию, затем отправляет `{"type":"ready","sessionId":"UUID","participants":[{"sessionId":"UUID","userId":"123","displayName":"Анна"}]}`.
4. После ready клиент буферизует события, получает HTTP-снимок, устанавливает его, отбрасывает события с seq ≤ snapshot.serverSeq и применяет оставшиеся по порядку. Это закрывает гонку между загрузкой и подпиской.
5. После COMMIT сервер рассылает всем, включая автора: `{"type":"operation","opId":"UUID","serverSeq":42,"object":{...}}`. Полный object совпадает с HTTP ACK. События доски отправляются строго по seq. Дубликаты игнорируются. HTTP ACK не должен заставлять клиент пропустить более ранние WS-события других объектов.
6. При reconnect/пропуске seq клиент повторяет подписку и полную загрузку снимка. Дельта-история не нужна в MVP. Неподтверждённые операции повторяются с прежним opId; конфликты обрабатываются по разделу 5.

При потере события в серверной очереди закрыть затронутые WS с 1013: клиент заново синхронизируется. Дополнительно каждые 10 секунд передавать `{"type":"sync","serverSeq":42}`. Отстающий клиент делает resync, поэтому потеря последнего события не остаётся незамеченной. При разрыве связи UI показывает «Нет соединения / не сохранено».

Лимит входящего preview не распространяется на исходящий полный object: исходящее operation-событие должно вмещать до 1 MiB JSON объекта плюс обёртку (лимит сообщения 2 MiB). Проверить настройки Drogon/proxy на длинном штрихе. Буфер медленного клиента ограничить 8 MiB; при переполнении закрыть с 1013, не накапливать память бесконечно. Изменения названия, пришедшие во время загрузки снимка, применять после снимка в порядке получения; sync дополнительно передаёт актуальное title для восстановления потерянного board.updated.

Временные сообщения клиента:

```json
{"type":"cursor","x":160,"y":200}
{"type":"stroke-preview","strokeId":"UUID","points":[[160,200],[162,202]],"color":"mint"}
{"type":"stroke-preview-end","strokeId":"UUID"}
```

Сервер сам добавляет sessionId/userId. Preview — заменяемый набор до 200 точек в координатах холста, не постоянная запись. Курсоры/preview не писать в БД. Суммарно ≤20 временных сообщений/с на сессию, ≤16 KiB каждое; лишние по частоте отбрасывать, неверную схему/размер закрывать с WS 1008/1009. Preview исчезает после end или 3 секунд без обновления; курсор скрывается через 10 секунд неактивности, участник остаётся до отключения.

Рассылать `presence.join` и `presence.leave` с sessionId/userId/displayName. WS ping каждые 15 секунд; нет pong 30 секунд — закрыть сессию. 11-е подключение отклонять с HTTP 429 при handshake. При истечении access token закрывать WS с 1008/AUTH_EXPIRED; клиент обновляет токен и получает новый ticket. После удаления участника закрывать его WS этой доски не позднее 1 секунды после COMMIT; последующие HTTP запрещены. Входящие временные события тоже проверять по текущему доступу.

## 7. Работа одному и приглашение по ссылке

Новая доска доступна только owner. Знание boardId не даёт прав.

| Метод и путь | Поведение |
| --- | --- |
| POST /api/v1/boards/{id}/invite | Только owner; создать/заменить ссылку → `{url,expiresAt}`; прежняя перестаёт работать |
| DELETE /api/v1/boards/{id}/invite | Только owner; отключить приглашение → `{revoked:true}`; повтор безопасен |
| POST /api/v1/board-invites/accept | Авторизованный пользователь отправляет `{token}` → `{boardId,role}`; добавить editor, повтор не создаёт дубль |

Ссылка многоразовая, действительна 7 суток. Токен — 32 криптографически случайных байта в base64url, в БД только SHA-256. URL `${PUBLIC_APP_URL}/#invite=<token>`: fragment не попадает в HTTP-логи. Фронтенд удаляет fragment после чтения, временно сохраняет приглашение в sessionStorage до завершения входа. Без аккаунта сначала регистрация/вход, затем принятие. Не отправлять токен сторонним сервисам.

Истёкший/отозванный/неизвестный token → 404 INVITE_INVALID. Owner при принятии своей ссылки остаётся owner. После принятия членство постоянно: доска появляется на другом устройстве после входа в тот же аккаунт.

Отзыв ссылки **не удаляет уже вступивших**. Для этого DELETE members. При удалении editor атомарно отзывать текущую ссылку всей доски, чтобы он не вступил повторно по старой ссылке. Owner при необходимости создаёт новую. Почтовая рассылка не нужна.

Принятие приглашения, его замена/отзыв и удаление участника сериализуются транзакционно по строке boards. Повтор DELETE уже отсутствующего участника возвращает успех, но не отзывает новую ссылку повторно.

## 8. Файлы: хранение и доступ с других устройств

- POST `/api/v1/boards/{id}/attachments`: multipart, одно поле file, заголовок `Idempotency-Key: <UUID>` (upload_id). Только owner/editor.
- HTTP 201 после надёжной записи → `{id,originalName,mime,size,sha256,downloadUrl}`. URL относительный: `/api/v1/boards/{id}/attachments/{fileId}`, не публичный.
- Повтор ключа тем же автором в той же доске с теми же байтами/именем → прежнее вложение, HTTP 200. Другие байты/имя → 409 UPLOAD_ID_REUSED.
- GET по downloadUrl проверяет членство и отдаёт исходные байты. Для картинки клиент делает авторизованный fetch и показывает Blob URL. Документы скачиваются.
- Создавать image/file-объект только после успешного upload и только со вложением той же доски. Ошибка загрузки не должна создавать ложную готовую карточку.

Форматы: PNG/JPEG/WebP/GIF, PDF/DOC/DOCX/XLS/XLSX/PPT/PPTX/TXT/MD/CSV/ODT/ODS/ODP/RTF. До 20 MiB (20 971 520 байт) на файл; до 200 MiB на доску, включая вложения удалённых объектов и пока неиспользуемые загрузки. До 10 файлов в одной вставке — отдельные запросы клиента. Multipart body limit API/proxy — 21 MiB, размер самого файла проверять отдельно. Параллельные upload не обходят квоту: резервирование/проверка атомарные. JSON-only filter на multipart не применять.

Проверять сигнатуру/структуру файла, не только MIME/расширение. Текстовые файлы — UTF-8 без NUL. MIME в ответе вычисляет сервер. ZIP-контейнеры Office/ODF проверять с лимитами памяти/времени, не распаковывать на диск. HTML/SVG/исполняемые файлы отклонять с 415. Документы не исполнять. Имя очистить от путей/управляющих символов, максимум 255 символов; storage_key генерирует сервер. Ответ: Content-Disposition attachment с безопасными filename/filename*, X-Content-Type-Options nosniff, Cache-Control private,no-store. Thumbnail, встроенные превью документов и Range не обязательны.

Запись: временный файл → завершение записи/fsync → атомарное переименование в том же volume и синхронизация каталога → фиксация метаданных БД → ACK. Сбой БД может оставить сироту на диске, но подтверждённая запись не должна ссылаться на незаписанные байты. Временные файлы/сироты без строки БД старше 24 ч очищать отдельной задачей, исключая активные загрузки.

Подтверждённые вложения в MVP автоматически **не удалять**, даже если объект удалён/не создан. Это сохраняет restore и повтор upload; такие вложения продолжают занимать квоту. Очистка подтверждённых вложений — будущая функция.

## 9. Docker, конфигурация и одна команда запуска

Бэкендер предоставляет:

1. Multi-stage Dockerfile: сборка из C++ исходников внутри образа, совместимые runtime-библиотеки внутри образа, запуск не от root. Не использовать host-бинарник build/petty_plusik. Зафиксировать версии образов/зависимостей.
2. compose.yaml: db (PostgreSQL), migrate (одноразовые миграции), api, web (текущий статический frontend + reverse proxy). Порядок: healthy db → успешный migrate → api → web. БД/API не публиковать наружу; web публикует `127.0.0.1:${APP_PORT:-4173}`.
3. Именованные volumes postgres_data и board_files. Файлы API только в board_files, не в удаляемом слое контейнера. Пользователь приложения PostgreSQL не superuser.
4. .env.example: APP_PORT, POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD, JWT_SECRET, PUBLIC_APP_URL, ALLOWED_ORIGINS; только заглушки секретов. Настройки API из env/документированного config, без зависимости от случайного cwd/../config.json.
5. GET /health/live → 200 при работающем процессе; /health/ready → 200 только при доступной БД, применённых миграциях и доступном для чтения/записи файловом volume, иначе 503. Без секретов. Compose проверяет readiness.
6. Compose/proxy-конфигурацию и инструкции для подключения к существующему `frondent/start.mjs --docker`. Этот новый режим реализует frontend-разработчик: `docker compose up --build` в foreground с явными путями и project name ryadom. Ctrl+C останавливает только свой проект, volumes остаются. В backend README дать также прямую эквивалентную команду.

Первый запуск с установленными Docker/Compose и заполненным env создаёт БД/схему без ручного SQL. Скрипт не устанавливает Docker, не запускает системную PostgreSQL, не меняет ОС. Сборка образов может скачивать зависимости: явно указать это, описать офлайн-вариант с заранее подготовленными образами/docker load. В рамках написания этого ТЗ ничего не скачивать и не развёртывать.

Занятый порт → понятная ошибка с предложением APP_PORT=4174; без kill/pkill и автоматического подбора порта. Proxy поддерживает HTTP API, upload и WS Upgrade. Текущий scripts/serve.mjs с узким whitelist требует доработки; не считать его уже совместимым. Docker-контекст web согласовать с frontend-разработчиком.

`docker compose down` сохраняет volumes. `down -v` удаляет данные: не включать в обычную остановку, явно пометить разрушительной командой в инструкции.

Проверить JWT expiry, атомарную ротацию refresh и запрет повторного refresh, существующий logout всех устройств; logout закрывает связанные WS ≤1 с. Для MVP повторный вход после закрытия браузера допустим: токены в памяти фронтенда, данные остаются в аккаунте. Секреты не писать в git/логи. SQL параметризовать. Старые note-role маршруты не должны выдавать доступ к boards. Уже скачанный участником файл технически отозвать нельзя.

Для будущего размещения документировать HTTPS/WSS, разрешённые Origins и отсутствие wildcard CORS. Сейчас только локальный запуск, без деплоя.

## 10. Долгое хранение, backup и restore

У досок и подтверждённых файлов нет автоматического срока удаления. Истечение токенов/приглашений и месяц неактивности не удаляют данные. Перезапуск API, БД, контейнеров, обновление образов с теми же volumes сохраняют подтверждённые операции.

Volumes — не резервная копия. Предоставить backup/restore скрипты и инструкцию. Простой согласованный backup: временно остановить api, оставить db; выполнить pg_dump custom format, архивировать board_files, записать manifest с временем/версией схемы/контрольными суммами, затем вернуть api в прежнее состояние запуска. Предупредить о паузе редактирования. На ошибке не выдавать неполный архив за успешный.

Restore проверить в **отдельном пустом** Compose-проекте/volumes: восстановить БД и файлы одной копии, запустить совместимую версию приложения, открыть доску, сравнить SHA-256 файлов. Рабочие данные без отдельного подтверждения не перезаписывать.

В инструкции: ежедневный backup, хранить последние 7 успешных копий вне исходных volumes, желательно на другом носителе. Расписание настраивает оператор; не устанавливать скрытый системный cron. При полной утрате диска допустима потеря не более интервала backup (24 ч); обычный перезапуск не теряет ни одной подтверждённой операции.

## 11. Порядок реализации и передача фронтенду

1. Docker-сборка, PostgreSQL, миграции, health, проверенная авторизация.
2. Создание/список/загрузка досок, транзакционные операции и права.
3. Приглашение, постоянное членство и отзыв доступа.
4. WS-события, presence/preview, восстановление и конфликтные ответы.
5. Upload/download, квоты, backup/restore, сквозная проверка.

Передать исходники, SQL-миграции, Dockerfile/Compose/proxy, .env.example, README с командами запуска/остановки/backup/restore, **OpenAPI всех HTTP-маршрутов** и отдельный JSON-контракт всех WS-событий/ошибок. Дать исполняемые curl-примеры: register/login → create board → create object → invite → accept вторым аккаунтом → upload → создать file-объект → download. Формат регистрации описать по существующему API. Тестовые аккаунты создавать только в тестовой БД, не поставлять production-пароли.

Затем frontend-разработчик подключает: список серверных досок и URL `/#board=<UUID>`; вход/регистрацию и возврат в приглашение; очередь HTTP и WS вместо локальной совместности; честные статусы сохранения; конфликт текста; серверные вложения; кэш по userId/boardId; proxy и --docker. После logout чужой кэш не показывать.

Старую локальную доску не мигрировать автоматически: предложить явный импорт с загрузкой вложений и новыми UUID, включая старые строковые demo-ID. Статический demo-asset не является серверным attachment.

## 12. Приёмка: что обязательно проверить

Тестировать реальный C++ API + PostgreSQL + файловое хранилище, не только mocks. До подключения UI сценарии выполняет HTTP/WS-тестовый клиент; после подключения повторить сквозные сценарии в браузерах.

| № | Действие | Ожидаемый результат |
| --- | --- | --- |
| 1 | Запуск с пустыми volumes по README, затем повторный запуск | Схема создаётся автоматически, регистрация работает, повтор безопасен |
| 2 | А создал все 6 типов объектов и вошёл с другого устройства с чистым браузером | Та же доска, текст/геометрия/цвета/файлы без ручного импорта |
| 3 | Б принял ссылку; В знает только ID | Б editor, доска в списке; В получает 404 для доски, файла и WS |
| 4 | А и Б 60 секунд параллельно рисуют и двигают разные объекты | Подтверждённые изменения не теряются, итоговые снимки совпадают |
| 5 | Два клиента меняют один текст с одной baseRevision | Один успех, один 409 с полным объектом; UI сохраняет второй черновик |
| 6 | Потерять HTTP ACK после записи, повторить opId | Прежний ACK, без повторного действия/seq; другой payload под тем же ID отклонён |
| 7 | Б офлайн 30 с, А меняет доску; вернуть Б | Снимок восстанавливается, очередь повторяется, конфликты не затирают А |
| 8 | Изменение между ready и снимком; отдельно потеря последнего WS-события | Снимок+буфер корректны; sync выявляет отставание максимум за 10 с |
| 9 | А загрузил PNG/PDF; Б скачал; перезапустить api/db/web и браузеры | Файлы доступны, SHA-256 оригиналов совпадает |
| 10 | Файл >20 MiB, SVG/HTML, чужой attachmentId; параллельное превышение 200 MiB | Отклонено, квоты не обходятся, ложных готовых карточек нет |
| 11 | Отозвать ссылку, затем удалить Б с открытым WS | Ссылка не работает; членство живёт до удаления; после удаления WS закрыт ≤1 с и HTTP запрещён |
| 12 | Аварийно завершить API после ACK; отдельно отключить БД | После рестарта данные есть; при недоступной БД нет ложного ACK, ready=503 |
| 13 | 10 сессий по 2 операции/с 60 секунд, затем 11-я | 1200 операций без потерь (менять разные существующие объекты); 11-я отклонена |
| 14 | Backup → restore в отдельный пустой проект | Аккаунты/доски/участники/объекты и SHA-256 файлов совпадают |
| 15 | До запуска занять APP_PORT другим процессом | Понятная ошибка, чужой процесс продолжает работать |
| 16 | По тестовым часам прошло 30 дней, токены/ссылка истекли; войти заново | Данные на месте, ранее вступивший участник сохранил доступ |
| 17 | Delete/restore объекта с файлом; undo с устаревшей revision | Файл сохранён; stale undo отклонён, чужая правка на месте |

Для теста 13: локальный Docker host ≥4 CPU/4 GiB RAM, loopback-сеть, каждый клиент последовательно меняет свой объект с актуальной revision. p95 от отправки HTTP до WS-события у другого клиента ≤500 мс. Зафиксировать параметры стенда и результаты в отчёте.
