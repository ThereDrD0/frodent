# Бэкендеру: совместная доска Рядом

> Архивный handoff. В текущем репозитории самостоятельный Python API находится в [`backend/`](../backend/README.md) и запускается через `start-docker.sh`. Соседний C++-проект для работы не нужен.

> Архив: актуальное, конкретизированное MVP-ТЗ находится в [BACKEND_MVP.md](BACKEND_MVP.md). При расхождениях использовать его: HTTP-операции + WS-события, owner/editor, серверное хранение, приглашения и Docker. Текст ниже сохранён как история первоначального предложения.

Это актуальное задание вместо редактора заметок. C++-проект не изменён. Нужен аналог простой Miro-доски: несколько людей одновременно рисуют, двигают объекты, пишут текст и добавляют изображения/документы.

## Что уже сделано на фронтенде

Полотно с панорамированием и масштабом; стикеры, текст, прямоугольники и свободные штрихи; перетаскивание и изменение размера; отмена/повтор; изображения и документы через drag-and-drop, выбор файлов и clipboard. Файлы пока хранятся как Blob в IndexedDB, растровые изображения отображаются на доске, документы скачиваются по двойному клику. Полная резервная копия `.ryadom` включает вложения.

Одновременная работа реализована **только между вкладками одного browser origin**: BroadcastChannel передаёт присутствие и временный рисунок, IndexedDB хранит объекты с проверкой revision. Это не серверный протокол и не работа разных пользователей/устройств. При конфликте текста локальный вариант сохраняется отдельным объектом. Доступ по ссылке, удалённые курсоры и передача вложений между устройствами ждут работы ниже.

Существующий C++ сервер уже используется клиентом для:

| Действие | Существующий маршрут | Тело/результат |
| --- | --- | --- |
| Вход | POST `/api/v1/users/login` | `{email,password}` → `data.access_token` |
| Новый снимок | POST `/api/v1/notes` | `{title:"[Доска] …",content:"JSON"}` → `data.id` |
| Добавить сохранённый снимок на полотно | GET `/api/v1/notes/{id}` | `data.content` → проверка формата и новые локальные IDs |

Access token хранится только в памяти вкладки, refresh token не сохраняется. Ошибки 401/503 отображаются. Сохранение — только явное создание новой заметки, **без фонового PATCH целой доски**. Снимки не включают байты файлов; у таких объектов показано отсутствие оригинала. Это временное использование нынешнего API, не совместное редактирование. Через Node-сервер фронтенда проксируются только указанные маршруты на `127.0.0.1:BACKEND_PORT`; бизнес-логика остаётся в C++.

## 1. Повторно использовать текущую авторизацию и права

Оставить `users`, JWT, `users_notes`, роли owner/editor/viewer. Можно использовать `notes.id` как ID доски и `notes.title` как название, добавить таблицы объектов/операций/вложений, связанные с этой записью. `notes.content` временно остаётся местом для старых снимков; не нужно менять его при каждом движении мыши.

Новые контроллеры условно: `BoardController`, `BoardEventsController` (Drogon WebSocket), `AttachmentController`. Это предложения для C++-проекта, а не уже созданные файлы.

Сервер должен проверять роль на каждой операции и отдаче файла, включая уже открытый WebSocket. `addRoleByUserId` сейчас принимает произвольную строку: разрешить только enum viewer/editor, передачу owner вынести отдельно. Создание доски должно явно назначать owner. Добавить список участников и отзыв доступа.

## 2. Модель объектов и начальная загрузка

Предлагаемые маршруты:

- POST `/api/v1/boards` → создание доски и owner.
- GET `/api/v1/boards` → список доступных досок с title, updated_at, role.
- GET `/api/v1/boards/{id}` → согласованный снимок `{id,title,role,serverSeq,objects,attachments}`.
- POST `/api/v1/boards/{id}/operations` → тот же протокол устойчивых изменений, что и WebSocket, для отправки/повтора без постоянного соединения.

Формат одного объекта сейчас:

```json
{
  "id": "UUID",
  "type": "sticky",
  "x": 120,
  "y": 180,
  "w": 240,
  "h": 180,
  "text": "Наша идея",
  "color": "mint",
  "revision": 4,
  "deleted": false,
  "created": 1788860000000
}
```

Типы: sticky, text, shape, stroke, image, file. Цвета: mint, blue, neutral. У stroke — `points: [[x,y],…]` относительно начала объекта; у файла — имя в text, size, mime и серверный attachmentId. **Локальный blobId не является серверным ID.** Опциональные headline/small — только визуальные варианты текста, не права доступа.

Локальные ограничения: 1000 видимых объектов, 20 000 символов на объект, 10 000 точек на штрих, конечные координаты в пределах ±1 000 000. Сервер проверяет схему сам. Размеры положительны; тип и цвет — whitelist. На сервере серверное время и ревизия авторитетны.

Таблицы: `board_objects(board_id,object_id,type,payload,revision,deleted_at)`; `board_operations(board_id,server_seq,op_id,actor_id,payload,created_at)`; `board_attachments(id,board_id,storage_key,original_name,mime,size,sha256,status)`. Уникальность `(board_id,object_id)`, `(board_id,op_id)`, `(board_id,server_seq)`. Конкретный SQL и миграции предоставляет бэкендер.

## 3. Одновременные изменения и восстановление соединения

Добавить WebSocket `/api/v1/boards/{id}/events`. Для браузерного handshake предпочтителен одноразовый короткоживущий ticket, полученный авторизованным POST `/api/v1/boards/{id}/session`. Не помещать долгоживущий access token в URL. Проверять Origin, срок ticket и доступ к доске; повторное использование ticket запрещено.

Устойчивая операция:

```json
{
  "type": "operation",
  "opId": "UUID",
  "clientId": "UUID",
  "objectId": "UUID",
  "baseRevision": 4,
  "action": "update",
  "patch": {"x": 160, "y": 200}
}
```

Actions create/update/delete/restore. Пользователь определяется по сессии, а не по присланному actorId. Update допускает только изменяемые поля. В одной DB-транзакции проверить доступ и baseRevision, сохранить объект, увеличить revision/serverSeq и записать opId. ACK/рассылку отправлять **после commit**. Повтор opId возвращает прежний результат, не применяет действие дважды.

При устаревшей baseRevision вернуть 409 (или событие conflict) с актуальным объектом. Не молча перезаписывать. Разные объекты должны меняться независимо; нельзя блокировать всю доску на редактирование одного стикера. Undo клиента отправляет обратную операцию с проверкой ревизии и не отменяет чужие действия.

После reconnect клиент передаёт lastServerSeq, получает пропущенные операции, затем повторяет неподтверждённые opId. Если история уже очищена — новый согласованный снимок с seq. Удаления сохраняются tombstone достаточно долго, чтобы офлайн-клиент не воскресил объект. Если несколько экземпляров сервера — нужна общая рассылка, а не только память одного процесса.

**Один текст одновременно:** CAS предотвращает потерю текста, но не объединяет посимвольный набор. Для полноценного одновременного ввода в один блок согласовать CRDT/OT для текстовых объектов и его бинарный/JSON-протокол. Хранить операции и снимки, повторно проверять права. До этого клиент должен показывать конфликт и сохранять оба варианта; нельзя называть last-write-wins совместным текстовым редактором.

## 4. Временные курсоры и процесс рисования

Отдельные эфемерные события: cursor, selection, stroke-preview, editing, leave. Они не увеличивают revision и не пишутся в БД. Ограничить частоту, размер пакета и TTL; не показывать «пишет» навсегда после обрыва. Конечный штрих сохраняется устойчивой операцией. Присутствие показывать только для реально подключённых сессий.

Текущий лимит WebSocket в конфигурации — 128 КБ: длинный штрих может не поместиться. Согласовать фрагменты штриха или ограниченные пакеты точек, например до 200 за preview. Не увеличивать лимит без проверки размеров и rate limiting на сервере.

## 5. Документы и изображения

- POST `/api/v1/boards/{id}/attachments` — multipart/form-data, только editor/owner. Не навешивать нынешний JSON-only parser на multipart.
- Ответ после надёжного сохранения: `{id,name,mime,size,sha256,downloadUrl,previewUrl?}`.
- GET `/api/v1/boards/{id}/attachments/{fileId}` — проверка членства, отдача оригинала с безопасным Content-Disposition, nosniff, при необходимости Range.
- Удаление/очистка — только с учётом всех ссылок на файл, истории и срока восстановления. Клиентская отмена удаления объекта не должна потерять файл.

Фронтенд принимает PNG/JPEG/WebP/GIF и PDF/DOC/DOCX/XLS/XLSX/PPT/PPTX/TXT/MD/CSV/ODT/ODS/ODP/RTF, до 20 МБ каждый, до 10 за вставку. В текущем C++ config body limit **1 МБ**, его нужно согласовать с multipart. Проверять реальный тип/сигнатуру, размер и общий лимит доски; имя пользователя не использовать как путь. Для preview растровых изображений делать ограниченные по размеру thumbnails. HTML/SVG/Office не исполнять в origin приложения. Документы можно сначала отдавать только для скачивания; PDF/Office-превью — отдельная необязательная задача.

Upload и создание объекта должны выдерживать повтор и обрыв: сначала подтверждённый attachment, затем операция объекта. Прерванные и осиротевшие загрузки чистить по TTL. Локальные blob: URLs между устройствами не работают — другим участникам нужен авторизованный серверный ресурс. Для image/img с Bearer клиент может получать Blob через fetch; не делать приватные файлы публичными ради превью.

## 6. Что ещё потребуется фронтенду после готовности API

В нынешнем интерфейсе одна локальная доска. После согласования endpoint/schema подключить выбор серверной доски, постоянную сессию с refresh, обмен операциями вместо BroadcastChannel, устойчивую очередь неподтверждённых действий, upload/download вложений, реальные участники/роли и обработку reconnect/conflict. Расширить whitelist localhost-прокси и CSP только под фактически необходимые маршруты. WebSocket-клиент нового протокола пока не подключён — endpoints отсутствуют.

## Приёмка

Два разных пользователя в независимых браузерах открывают одну доску: параллельные штрихи и разные стикеры не теряются; изменение одного текста не затирает второй вариант; курсоры исчезают после отключения. Вложенная картинка и PDF доступны обоим после reload. Повтор opId не дублирует объект. Reconnect после офлайна догружает пропущенное. Viewer не пишет/не загружает; отзыв доступа прекращает WebSocket и чтение файлов. Undo не отменяет чужую ревизию. Ошибка загрузки не создаёт ложный готовый файл.

Сейчас запуск настоящего бинарника дополнительно блокируют отсутствующие shared libraries; PostgreSQL и миграции требуется подготовить отдельно. См. `STARTUP.md`. Контракт проверен на mocks, не на работающем C++ API. Исходный сервер и система в этой сессии не менялись.
