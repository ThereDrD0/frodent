# Задание для бэкендера

C++-проект `../todo_list_cpp` изучен только чтением. Ни код, ни конфигурация, ни база не изменены; сервер не запускался. Этот фронтенд первого этапа работает локально. Ниже — контракт следующего этапа; это не список уже подключённых функций.

## Что уже есть в исходниках

| Назначение | Маршрут | Контракт |
| --- | --- | --- |
| Регистрация | POST `/api/v1/users/register` | `UserController` |
| Вход / обновление сессии | POST `/api/v1/users/login`, POST `/api/v1/users/refresh` | `UserController` |
| Текущий пользователь | GET `/api/v1/users/me` | `AuthFilter` |
| Список заметок | GET `/api/v1/notes` | `data: [{id, title}]` |
| Создание | POST `/api/v1/notes` | `{title, content?}` |
| Чтение | GET `/api/v1/notes/{id}` | `data: {id,title,content,created_at,updated_at,role}` |
| Изменение | PATCH `/api/v1/notes/{id}` | `{title?, content?}`, роли editor/owner |
| Удаление | DELETE `/api/v1/notes/{id}` | Только owner, физическое удаление |
| Выдача роли | POST `/api/v1/notes/roles/{id}` | `{login,role}`, только owner |

Ответы обёрнуты в `{status: "Success", message, data?}` или `{status: "Error", message, errors?}`. Защищённые маршруты ожидают `Authorization: Bearer <token>`.

## Минимум для безопасного подключения

1. **Защита от потери чужих изменений.** В текущем PATCH нет версии/условного обновления: две записи могут перезаписать друг друга. Добавить монотонный `version` в GET и PATCH. PATCH принимает ожидаемую версию, SQL обновляет только при её совпадении и увеличивает её атомарно. При конфликте — 409 с актуальными данными. Версии должны проверяться в БД, а не отдельным SELECT перед UPDATE.
2. **Поля списка.** Сейчас SQL выбирает `updated_at`, но ответ возвращает только `id/title`. Вернуть `updated_at`, `created_at`, `role`, короткий `excerpt`, `version`. Все даты — ISO 8601 UTC с зоной. Поиск по полному содержимому потребует серверного поиска или отдельной загрузки документов; лучше добавить `?q=` и пагинацию.
3. **Роли.** Проверять whitelist `viewer/editor/owner` на сервере: `addRoleByUserId` сейчас принимает произвольную строку. Запретить изменение владельца через обычный endpoint выдачи роли. При создании явно назначать owner; проверить соответствующий DB default, так как контроллер не вызывает `setRole` при создании связи.
4. **Сессия и HTTP.** Согласовать фактические поля ответа входа/refresh и срок жизни токена. Предпочтительны access token в памяти и refresh через HttpOnly cookie; при cookie-авторизации определить CSRF/SameSite. Отдавать фронтенд и API с одного origin либо явно разрешить только нужный origin и OPTIONS. Тестовый сервер фронтенда сейчас намеренно не проксирует API и имеет CSP `connect-src 'none'`; при интеграции её нужно изменить на `'self'`.
5. **Ошибки.** Согласовать 401 для отсутствующей/истёкшей сессии, 403 для отсутствия прав, 404 для отсутствующей заметки, 409 для конфликта, 422/400 для проверки полей, 429 для лимитов. Сейчас отсутствие Authorization даёт стандартный 400, а пустая выборка `getNoteById` — 500. Добавить предельные размеры title/content и тела запроса; клиентский maxlength не заменяет серверную проверку.

## Чтобы сохранить функции интерфейса

- **Избранное:** персональное поле в `users_notes` и отдельное изменение; текущий «закреплённый» список — просто первые пять избранных.
- **Корзина:** soft delete с `deleted_at`, выборка корзины и восстановление. До появления этих маршрутов **не связывать** действие «В корзину» с существующим DELETE: он удаляет данные физически. Альтернатива — явно согласовать упрощение интерфейса с окончательным удалением и подтверждением.
- **Участники:** GET списка участников с ролями; добавление по login можно подключить к уже имеющемуся маршруту. Для удаления доступа нужен отдельный endpoint. Не показывать фиктивные аватары или присутствие.

## Совместное редактирование

Доступ нескольких людей к документу и редактирование в реальном времени — разные этапы. Сначала достаточно optimistic concurrency из пункта 1 и уведомления о новой версии (SSE/WebSocket либо согласованный polling). Клиент при 409 сохраняет свой черновик и предлагает сравнить версии; не повторяет PATCH вслепую.

Если нужен одновременный набор текста как в HackMD, отдельно согласовать CRDT/OT-протокол, хранение операций/снимков, reconnect, проверку прав при каждом обновлении и поведение при отзыве доступа. Обычная рассылка полного текста по WebSocket без разрешения конфликтов не решает потерю изменений. В текущих контроллерах такого протокола нет.

## Приёмка следующего этапа

Два независимых пользователя открывают одну заметку; viewer не может писать; editor не выдаёт роли и не удаляет; owner выдаёт/отзывает доступ. Одновременные PATCH с одной версией: ровно один успешный, второй 409. Перезапуск/обрыв соединения не теряет локальный черновик. Корзина восстанавливается. Ошибки сессии и сервера отображаются без ложного «Сохранено».
